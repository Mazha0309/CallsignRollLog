# AI 语音录入改造设计：多模态与 ASR 双模式 + 本地校对

日期：2026-10-07
状态：待实施
影响范围：`lib/services/ai_*`、`lib/widgets/ai_recognition_control.dart`、`lib/services/text_assistant*.dart`、`lib/providers/ai_recognition_settings_provider.dart`

## 1. 背景

现有实现是「录音 → 15 秒固定分段 → 网络 ASR → 把**累积全文**发给文字模型抽取字段 → 候选 → 人工复核」。

### 1.1 三个已确认的问题

**延迟**。`AiRecognitionRuntime.recognize` 是两次串行网络调用（`transcribe` 然后 `extractFields`）。`lib/widgets/ai_recognition_control.dart` 的 `_transcribeLiveChunk` 每 15 秒触发一次，把 `_joinedTranscript`（**至今为止的全部转写**）交给抽取，且同一时刻只允许一轮在飞（`_liveTranscriptionInFlight`）。因此：输入 token 随录音时长线性增长，一旦单轮耗时超过 15 秒，预览就永久落后。这是设计上的正反馈，不是参数问题。

**成本**。同上，每 15 秒一次且带累积全文，单条记录的输入量是 O(n²)。一轮 59 人点名会产生上千次调用。

**建议无用**。`lib/services/text_assistant_tasks.dart` 的 `_inlineSystemPrompt` 把任务定义为「规范化一个字段值」，并规定「无法安全规范化时原样返回」；`suggestInline` 又丢弃与输入相同的候选（`candidate == normalized` 直接 `return null`）。也就是说它**在结构上只能改格式**，而多数输入本来就不需要改格式。它同时是跟随按键触发的额外消费。

### 1.2 目标

现场主控念完一条，字段尽快出现，一眼能确认；关键字段不依赖模型是否走运；模型调用次数有上界且可数；**普通用户三步内把 AI 配好并能自查是否配通**。

## 2. 决定

| 决策 | 内容 |
| --- | --- |
| **本次范围** | **只做模式 A（多模态）**。模式 B 保持现状、冻结优化，仅作为备选可选项；其配置预设与体验改造推迟 |
| 两种模式 | **模式 A 多模态**（默认，只需一个多模态 profile）与 **模式 B ASR**（只需一个 ASR profile）。二者共享校对层、记录级上下文、额度与交互 |
| 模式 A 主路径 | **多模态单跳**：音频直接交给支持音频输入的模型，一次调用同时拿到转写与字段 |
| 校对层 | **复用本地数据库**：把模型给的字段值拿去和词库/历史/会话内记录比对，命中就写库中的规范写法 |
| 配置 | **预设驱动 + 连接测试**：选服务商、粘 Key、点测试，三步跑通；高级选项默认折叠（§8） |
| 用户可见内容 | **只显示格式化后的内容**：原始模型响应、异常、内部错误码一律不得进入界面（§13） |
| 上下文 | **记录级**：一条记录一个上下文，提交即销毁，记录之间不传递文本 |
| 额度 | 每条记录首调用之外的调用按**事件触发 + 硬上限**，默认 3、可调 1–5 |
| 删除 | 15 秒固定分段、累积全文、行内 LLM 建议 |

## 3. 模式 A 的主路径

```
录音 ──静音切分──▶ 多模态模型（一次调用）
                      │  返回 transcript + fields
                      ▼
                本地校对层（§4）
                      ▼
                 候选 → 复核面板（§7）→ 落字段
```

### 3.1 一次调用同时产出转写与字段

请求沿用已实现的 `input_audio` 通道（`lib/services/ai_recognition/http_providers.dart` 的 `_transcribeChatAudio`），但用途从「语音识别」改为「音频理解」，输出契约为：

```json
{
  "transcript": "把听到的原话转写下来",
  "fields": { "callsign": "…", "device": "…", "power": "…" },
  "uncertain": ["qth"]
}
```

- `transcript` 有两个用途：复核时给人看；救场时不必重新识别。
- `fields` 的键限定为现有集合：`callsign, device, antenna, power, qth, height, rstSent, rstRcvd, remarks`。**不返回 `time`，不返回主控呼号**（与现有一致，主控属于会话上下文）。
- `uncertain` 是可选数组，列出模型自认没把握的字段，供复核面板标黄。
- 音频格式：PCM16 WAV 已由 `lib/services/ai_audio_recorder.dart` 的 `Pcm16WavEncoder.encode` 在本地生成，直接 base64 发送；格式字段与 `audioDataEncoding` 由 provider profile 配置。

协议侧需要一个新用途：`AiProtocol.supports` 目前把 `openAiChatCompletionsAudio` 只登记给 `speechRecognition`，字段抽取只认纯文本协议。需要新增「音频 → 字段」的 kind，让同一协议既能出转写也能出字段。

### 3.2 静音切分

把固定 15 秒改为按停顿切分：在已有的 PCM16 流上计算 RMS，低于门限持续「静音时长」即切段，并设最长单段上限兜底。参数（静音门限、静音时长、最长段）可调，默认值在实施时用真实录音标定。

PCM 流不可用时（部分平台/设备）回退为**固定 4 秒窗口**，行为仍优于现状。

面板保留手动「说完这条」按钮：会场嘈杂时自动切分可能失效，人工触发是兜底。

### 3.3 记录级上下文

引入 `RecordContext`，只装本条记录的东西：已解析字段、本条记录的转写片段、本条确认与更正历史。生命周期为「开始一条 → 建立，提交或放弃 → 销毁」。

记录之间不传递任何文本或字段；跨记录唯一共享的是**词库**（持久数据，不是上下文）。这同时消除「越说越慢」和「上一条残余混入下一条」。

## 4. 本地校对层（复用数据库）

校对层是两种模式的必经环节，零网络、零成本，主要工作是**检索与消歧**而不是理解句子，因此不依赖语序。

### 4.1 匹配来源

| 来源 | 用途 | 现状 |
| --- | --- | --- |
| 四类词库（呼号/设备/天线/QTH） | 主力，写回库中规范写法 | 已有，`DictionaryProvider` 已加载 |
| 近期记录 | 词库未收录但本人常填的值 | 已有 `lib/services/ai_database_context.dart` 打分 |
| 会话内已填记录 | 同一轮里前面刚念过的呼号/设备 | 数据已有，需接入校对层 |

### 4.2 匹配强度递进

1. 归一化后精确匹配（去空格、大小写、全半角、常见异体字）。
2. 音标还原：`_natoCandidates` 已能把 `Bravo Golf Five D B L` 折成 `BG5DBL`。
3. 模糊匹配：沿用 `_callsignScore` 的编辑距离容错（呼号 ≤5 位容 1、更长容 2；含数字的型号放宽到 2），以及 `_closestWindowDistance`。

### 4.3 规则

- **命中即写库中的规范写法**，而不是模型给的原文。主控把「森海克斯 GT12」念成「森海 GT 十二」，记录里落的仍是词库里那条。既提准确率，又让数据自然归一。
- **数值类不查库**：RST 用 `5[1-9][1-9]` 或中文「五九」校验；功率复用 `extractExplicitPower`；高度校验「N 楼 / N 层 / N 米」。
- **冲突消歧**：同一段证据不得被两个字段占用；多类命中时按分数与类别优先级（呼号 > QTH > 设备 > 天线）裁决，最长匹配优先。
- **匹配不上就标记为新值**，进入复核面板等待确认，不静默写入。
- **降级**：词库为空或全新用户时覆盖率自然低，该模式仍可用，只是退回「依赖模型」。

### 4.4 学习闭环

复核确认的新值，经 `rust/src/api/dictionaries.rs` 的 `apply_dictionary_ai_changes`（`BEGIN IMMEDIATE` 事务 + stateToken 乐观锁）沉淀进词库。于是**下一轮相同的念法就能本地命中**，模型调用随之减少。这是本设计的复利。

## 5. 两种模式

用户在设置里二选一。二者的差别只在「识别与抽取」这一段，其余全部共享：§4 校对层、§3.3 记录级上下文、§6 额度、§7 交互。

**本次只实现模式 A。模式 B 保持现有实现不变（含现有的 15 秒分段与累积全文语义），只作为备选可选项存在，不做优化。** 因此下文凡涉及模式 B 的部分都是「维持现状」，不是工作项。

| | 模式 A：多模态（默认） | 模式 B：ASR |
| --- | --- | --- |
| 主路径 | 音频 → 多模态模型，一次调用同时出 transcript + fields | 音频 → ASR → 文字模型抽取 |
| **必需配置** | **一个多模态 profile** | **一个 ASR profile**（需声明字段抽取协议） |
| 可选配置 | 无 | 文字助手（配了则由它抽取；不配则用 ASR profile 自带的抽取协议） |
| 正常一条记录的模型调用 | 1 次 | 2 次 |
| 折算 1 小时音频成本 | ≈ 0.036 元 | ≈ 0.8 元（ASR）＋ 少量文本 |

**模式 B 的必需项只有一个 profile** 是现有代码就支持的：`AiRecognitionRuntime.extractFields` 在文字助手未启用或未配置时，会退到 `activeFieldExtractionProfile` 的 `ProtocolFieldExtractionProvider`。文字助手只是可选增强，不是必需。

### 5.1 模式 A 的救场

```
多模态请求失败（网络 / 超时 / JSON 不合法）
  → 退避重试一次
    ↓ 仍失败，且本记录已有转写
  → 用同一个多模态 profile 发纯文本请求做字段抽取
    ↓ 仍然失败
  → 面板提示，主控点「再听一句」重念
```

中段**复用多模态 provider 自己**——它是 OpenAI 兼容的 chat 端点，接受纯文本请求。因此模式 A 不需要另配文字助手，配置面只有一个 profile。

模式 A 完全不涉及 ASR，未配置 ASR 也不影响使用。触发原因写入候选 `metadata`，便于统计救场率。

### 5.2 模式 B 的救场

沿用现有语义，不新造：ASR 对录音期间失败的段落，在停止时重试一次（`ai_recognition_control.dart` 的 `_retryChunks`）；抽取失败时回到原始转写，由人工填写。

### 5.3 两种都配了

允许在设置里切换模式，也允许在复核面板上临时切到另一模式重试当前分段——把「救场」从自动链变成主控可掌控的动作。

### 5.4 默认模式与迁移

老用户升级后**行为不变**：只配了 ASR 的进模式 B，只配了多模态的进模式 A，两者都有则沿用上次选择。因此零迁移，现有 ASR 与文字助手配置原样可用。

设置页在多模态可用且当前处于模式 B 时给出提示：切到模式 A 可把音频成本降低约 20 倍，且只需一个配置项。不强制、不自动切换。

## 6. 成本与额度

### 6.1 成本对比

音频 token 折算：设计初稿引用的「秒 × 12.5」来自另一个模型的文档，**实测 `qwen3.8-omni-flash` 是约 7.5 token/秒**（4.0 秒音频 → `audio_tokens: 30`），1 小时 ≈ 27,000 token。详见 `docs/superpowers/notes/2026-10-07-bailian-audio-format.md`。

**但音频输入不是主要成本，输出才是。** 实测同一段 4 秒音频：

| 配置 | 耗时 | completion tokens | reasoning tokens |
| --- | --- | --- | --- |
| 默认（思考开启） | **174.3 s** | 13,636 | 13,540 |
| `enable_thinking: false` | **3.0 s** | 42 | 0 |

思考开启时输出 token 是音频 token 的 400 倍以上，且单条 174 秒在现场不可用。因此**预设必须携带 `body: {'enable_thinking': false}`**——这是服务商专属参数，也正是「预设」存在的理由。按关闭思考后的实测值估算，一轮 59 人点名的输出成本在**分**的量级。

| 路线 | 折算 1 小时音频 |
| --- | --- |
| `qwen3.8-omni-flash`（0.8 元/百万 token，全模态统一） | **≈ 0.036 元** |
| `qwen3.5-omni-plus`（音频 53 元/百万 token） | ≈ 2.39 元 |
| 豆包 Seed-ASR 2.0（纯 ASR） | 0.8 元 |
| 智谱 GLM-ASR-2512（纯 ASR） | ≈ 0.72 元 |

上表为文档原价，随地域与活动浮动，实施前需以控制台为准。

**结论：成本不再是主要约束。** 额度上限因此从「省钱」改为「避免无谓等待与幻觉叠加」。

### 6.2 额度规则

只有以下情况消耗额度：

1. 每条记录的首调用之后仍有未填字段，需要补救；
2. 主控又说了新的一段有效语音（补充或更正）。

**每条记录的首调用不占额度**——它必须发生一次（模式 A 是一次多模态调用，模式 B 是 ASR＋抽取），且成本可忽略。额度覆盖的是其后的补救调用。不消耗额度的情况：首调用已填满所有字段（直接不发）；没有新语音只是同一段重试（**禁止**，这就是要砍掉的自动重试）。

- 默认上限 3，设置内可调 1–5。
- 同一段文本或音频不重复请求。
- 传输失败允许一次退避重试，不扣内容额度，但每条记录的总尝试次数封顶。
- 第二次起只发缺失字段 + 新片段，不重发整条记录。
- 复核面板显示本轮已用调用次数（`n / 上限`），成本可见。

因此每条记录的调用次数上界是「1（首调用）+ 上限」，一轮 59 人点名最坏 59 × 4 = 236 次，实际远低于此。这个上界是可算的，不像现状随时长线性膨胀。

## 7. 确认与更正交互

在现有 `_AiRecognitionReviewPanel` 上改，不新造面板。

1. **字段带来源标记**，按**产出该字段的那次调用**划分：`本地命中`＝校对层在库中匹配到；`推断`＝首调用给出但库中无对应；`模型补充`＝其后的补救调用产出。一眼看出哪些需要人看。
2. **一键采纳只采纳高置信**：`全部采纳` 只吃 `本地命中` 项；`推断` 与 `模型补充` 必须单独确认或编辑。常见的「念完就确认」是一次点击。
3. **更正呈现为「旧值 → 新值」**，不是新增。一个字段只有一个值，更正进撤销栈。
4. **保留「再听一句」**：手动发起一次识别，占一次额度，用于主控让对方重念之后。
5. **不弹模态**：解析与救场在后台跑，字段逐项出现，等待期间可继续操作。

同一条记录内再次说话且某字段已有值时，判为更正（走现有 `AiCandidateGuard` 的 `replaceWithConfirmation`），不会出现两个呼号。记录提交后再改属于普通记录编辑，不唤醒 AI 上下文。

## 8. 配置流程

现有 ASR 配置要求用户自己选协议（四种）、填 API Base URL、填模型名、选鉴权方式、声明能力（支持的音频格式、大小上限、是否接受 prompt）、再调一堆请求选项（`lib/widgets/settings/ai_recognition_settings.dart` 的 `_AiProfileEditorDialog` 与 `_defaultRequestOptions`）。**正常用户在这里就会失败**，而且失败后没有任何自查手段，只能等到某次点名现场才发现配错了。

本节把「能跑起来」的路径压到三步。

### 8.1 三步配置

1. **选服务商**（预设下拉，带推荐标记）
2. **粘贴 API Key**
3. **点「测试连接」**

预设负责填掉其余全部字段：Base URL、协议、鉴权方式、能力声明、默认模型、请求选项。高级选项默认折叠，只有选「自定义」时才展开全量。

### 8.2 预设清单

本次只做模式 A 需要的两个：

| 预设 | 协议 | 说明 |
| --- | --- | --- |
| 阿里云百炼 | chat + `input_audio` | 模式 A 首选，`qwen3.8-omni-flash` |
| 硅基流动 | chat + `input_audio` | 便于横评开源音频模型 |
| 自定义 | 现有全量选项 | 兜底，任何预设都能被它覆盖 |

模式 B 专属的预设（火山引擎豆包、智谱）**推迟到做模式 B 时**。注意豆包不是 OpenAI 兼容，鉴权用 App ID + Token 走自定义头、请求体要模板——那种复杂度正是预设要藏起来的东西，所以做模式 B 时它是必需的。

**预设里的 Base URL、模型 ID、鉴权细节必须在实施时逐个实测确认**，不能照文档写死——服务商改接口的代价会直接落到用户身上。因此预设带版本标记，且任何时候都能被「自定义」覆盖。

### 8.3 连接测试

发送内置样例音频（`assets/ai/`，几秒、内容已知），跑完整链路，显示：识别到的文本、填出的字段、耗时。

这是普通用户**唯一能自查的手段**。同一份样例同时复用作 §10 的回归语料基线——它既是功能，也是测试夹具。

### 8.4 错误可读化

现在 UI 用 `error.toString()` 直接弹 SnackBar，用户看到的是 `AI_AUDIO_PCM16_UNSUPPORTED` 这类内部标识。改为按 `AiRecognitionErrorKind` 映射成「问题 + 下一步」：

| 现状 | 改为 |
| --- | --- |
| `missingCredentials` | 还没填 API Key |
| 401 / 403 | API Key 无效，或该 Key 没有这个模型的权限 |
| 404 | 模型名或 Base URL 不对，检查是否选错预设 |
| 超时 | 网络不通，检查是否需要代理 |
| `invalidConfiguration` | 协议与服务商不匹配，建议换回官方预设 |
| `AI_AUDIO_PCM16_UNSUPPORTED` | 该服务不接受 PCM，已自动改用 WAV |

### 8.5 配置项与迁移

| 设置项 | 变化 |
| --- | --- |
| 模式选择 | **新增**，默认按已配置内容推断（见 §5.4），不自动切换 |
| 多模态（音频理解）profile | **新增**，模式 A 的必需项。复用 `AiProviderProfile` 结构，新增 kind 与预设 |
| 语音识别（ASR profile） | 模式 B 的必需项；模式 A 不使用。改为预设驱动 |
| 文字助手 | 模式 B 的可选增强（不配则用 ASR profile 自带的抽取协议）；模式 A 不需要 |
| 慢路径上限 | **新增**，默认 3，范围 1–5 |
| 静音切分参数 | **新增**，门限/静音时长/最长段 |

迁移：现有 ASR 与文字助手配置原样保留，升级后进入模式 B，行为与现在一致（除分段与上下文的改动）；补一条多模态 profile 后即可在设置里切到模式 A。已有的自定义 profile 不强制转成预设——预设只是「新建时」的默认来源。凭据仍走 `AiCredentialStore` + 平台安全存储，不落 `shared_preferences`。

**删除**：`TextAssistantTasks.suggestInline` 及其调用链（`lib/widgets/log_form.dart` 的 `_requestInlineAiSuggestion` / `_adoptInlineAiSuggestion`）。已有的字典即时补全是确定性、零成本的，行内建议想做的事它本来就在做。

## 9. 既有缺陷的处理

探查中发现三处客观缺陷。按「本次只做模式 A」的范围，区分处理：

**纳入本次**：

- **Excel 导入泄漏 HTTP 客户端**：`lib/widgets/export_panel.dart` 的 `_importExcel` 创建 `createTextAssistantClient(...)` 后全程无 `client.close()`，每次导入泄漏一个客户端；字典与行内建议两条路径都有 `finally { client.close(); }`。这与模式无关，是纯粹的 bug。

**推迟到做模式 B 时**（两者都在文字助手链路里，属于模式 B 的地盘）：

- **文字助手不禁用重定向**：`lib/services/text_assistant.dart` 的 `_postJson` 用 `package:http` 默认跟随重定向，`Authorization` / `x-api-key` 可能被转发到其他 origin。ASR 的 `http_transport.dart` 已明确 `followRedirects = false`。
- **文字助手无响应体上限**：ASR 有 2MB 上限（`maxResponseBytes`），文字助手没有。

**同样推迟**：把 `languageHint` 接到转写调用上（`AiRecognitionRuntime.transcribe` 目前未传该参数，而 model/provider 与文档都声明支持「存在语言提示时发送」）。它只影响模式 B。

## 10. 前置实验与验收指标

### 10.1 前置实验（必须先做，结论决定模式 A 的主模型）

`qwen3.8-omni-flash` 的结构化输出支持情况未能从文档确认，而 `qwen3.5-omni-flash` 明确**不支持**。这直接决定 JSON 合法率与模式 A 的救场触发频率。模式 B 沿用现有实现，不参与本实验。

做法：取真实点名录音（至少 20 条，覆盖呼号字母混读、中文 QTH、设备型号混读），对三个候选模型跑同一份 prompt：`qwen3.8-omni-flash`（首选）、`qwen3.5-omni-plus`（支持 JSON Object 的保底），以及硅基流动上的一个开源音频模型作对照。比较：

| 指标 | 说明 |
| --- | --- |
| JSON 合法率 | 一次解析成功、无需重试的比例 |
| 呼号准确率 | 逐字符正确率，以及**经本地词库校正后**的最终正确率 |
| 端到端耗时 | P50 / P95 |
| 字段召回 | 各字段被正确填出的比例 |
| 单条成本 | 实测 token 用量折算 |

**同一批语料同时跑一遍现有模式 B 作为基线**——否则无法证明模式 A 真的更好，只能证明它能跑。

若 `qwen3.8-omni-flash` 的 JSON 不稳，主模型换 `qwen3.5-omni-plus`（支持 JSON Object，约 2.4 元/小时，仍远低于预算敏感线）。

### 10.2 验收指标

- **本地校对覆盖率**：不依赖模型补充、仅靠库匹配即填对的字段比例。
- **端到端延迟**：从切段到候选出现，P50 / P95，需与模式 B 基线对比。
- **每条记录平均模型调用次数**（含补救调用）。
- **模式 A 的救场触发率**与**补救层级分布**。
- **配置成本**：从打开设置到「测试连接」通过所需的步骤数与耗时，目标 ≤ 3 步；以及**连接测试的失败可诊断率**（错误提示能指出下一步的比例）。
- **格式合规**：界面字符串中出现的内部标识、错误码、异常文本数量为 **0**（§13）。用一条遍历所有用户可见文案的测试兜住，防止后续改动把 `error.toString()` 之类重新引回来。
- **呼号最终正确率**：分「模型原始」与「经本地词库校正后」两个数，用于确认校对层真的在起作用。
- 回归方式：表驱动语料（转写 + 期望字段），纳入现有 `flutter test`。

## 11. 非目标

- 不做本地（端侧）语音识别。若将来要离线可用，那是另一个设计。
- 不做流式增量转写（WebSocket 逐字出）。本设计接受「一句话一次」的交互，不追求亚秒级。
- **本次不优化模式 B**：不重构其分段、上下文、配置与错误提示，保持现有行为；相关缺陷与预设推迟。
- **不自动在两种模式之间切换**；切换由用户发起（设置里或复核面板上）。
- 不改动协作、同步、导出等与 AI 无关的部分。
- 不引入对话历史。每次请求都是无状态单轮。

## 12. 风险

| 风险 | 应对 |
| --- | --- |
| 多模态模型 JSON 不稳定 | 模式 A 的补救链是强制项；§10.1 先实测再定模型 |
| 模型幻觉呼号 | 本地词库模糊校正 + `AiCandidateGuard` 强制人工确认，不静默写入 |
| 内部错误码泄漏到界面 | §13 硬规则：只渲染格式化文案；原始细节只进日志，界面只留「复制诊断信息」 |
| 模式 A 的文本补救依赖服务商接受纯文本请求 | §10.1 一并验证；不接受则补救退到「人工重念」，不阻塞主流程 |
| 会场嘈杂导致静音切分失效 | 保留手动「说完这条」按钮；回退固定窗口 |
| 音频后端的字段名/采样率各家不同 | 沿用 profile 里已有的 `audioFormat` / `audioDataEncoding` / `requestTemplate` 开关，不按模型名猜 |
| 单价随活动变化 | 复核面板显示调用次数；成本按实测折算而非按标价承诺 |
| 记录级上下文被误用（跨记录复用） | `RecordContext` 只在开始记录时创建，提交即销毁，并在测试中断言不跨记录 |
| 两种模式的候选语义分叉 | 校对层、`AiCandidateGuard`、复核面板对两种模式共用同一套候选结构，模式只决定候选由谁产出 |
| 预设随服务商接口变动而失效 | 预设带版本标记与来源链接；「自定义」始终可用；连接测试能在用户现场立刻暴露失效，而不是等到点名时 |
| 连接测试的样例音频被误当作真实数据上传 | 样例是内置合成音频，不含任何用户内容；测试文案明确标注「会发送到该服务商」 |

## 13. 格式约束：用户只看到格式化后的内容

**硬规则**：任何面向用户的界面只渲染经过格式化与本地化的内容。原始模型响应、原始异常、内部错误码一律不得直接进入界面。

### 13.1 禁止出现的内容

- `error.toString()` 与异常堆栈
- 内部错误码：`AI_AUDIO_PCM16_UNSUPPORTED`、`AI_AUDIO_ENCODER_UNSUPPORTED`、`AI_AUDIO_EMPTY`、`AI_RECOGNITION_DISABLED`、`missingCredentials`、`invalidConfiguration`、`StateError('TEXT_ASSISTANT_*')` 等
- HTTP 状态行与响应体片段（现在会经 `AiRecognitionException.responseBody` 进入提示）
- 模型原始响应：JSON 文本、``` 围栏、`reasoning_content` / 思维链

### 13.2 落地方式

新增一个格式化层，把 `AiRecognitionException`、`AiRecognitionErrorKind` 以及文字助手的 `StateError` 统一映射成「问题 + 下一步」的本地化文案（映射表见 §8.4）。

覆盖四个位置：错误提示、模型输出渲染、连接测试结果、复核面板。

### 13.3 诊断信息不进界面

原始细节仍然保留，但只写入日志文件。界面上提供「复制诊断信息」按钮，需要反馈问题的人自行取用——**普通用户看不到，能反馈的人拿得到**。

### 13.4 唯一的例外：识别原文

复核面板需要展示模型返回的 `transcript`，供人工判断字段是否正确。严格按字面它属于模型原始输出，因此按例外处理：

- 默认折叠，需要时展开
- 明确标注「识别原文」
- 不参与字段渲染，不作为面板主内容

若将来判定连它也不该显示，改为仅呈现字段值与来源标记即可，不影响其余设计。
