# AI 语音录入改造设计：多模态主路径 + 本地校对 + LLM 救场

日期：2026-10-07
状态：待实施
影响范围：`lib/services/ai_*`、`lib/widgets/ai_recognition_control.dart`、`lib/services/text_assistant*.dart`、`lib/providers/ai_recognition_settings_provider.dart`

## 1. 背景

现有实现是「录音 → 15 秒固定分段 → 网络 ASR → 把**累积全文**发给文字模型抽取字段 → 候选 → 人工复核」。

### 1.1 三个已确认的问题

**延迟**。`AiRecognitionRuntime.recognize` 是两次串行网络调用（`transcribe` 然后 `extractFields`）。`lib/widgets/ai_recognition_control.dart` 的 `_transcribeLiveChunk` 每 15 秒触发一次，把 `_joinedTranscript`（**至今为止的全部转写**）交给抽取，且同一时刻只允许一轮在飞（`_liveTranscriptionInFlight`）。因此：输入 token 随录音时长线性增长，一旦单轮耗时超过 15 秒，预览就永久落后。这是设计上的正反馈，不是参数问题。

**成本**。同上，每 15 秒一次且带累积全文，单条记录的输入量是 O(n²)。一轮 59 人点名会产生上千次调用。

**建议无用**。`lib/services/text_assistant_tasks.dart` 的 `_inlineSystemPrompt` 把任务定义为「规范化一个字段值」，并规定「无法安全规范化时原样返回」；`suggestInline` 又丢弃与输入相同的候选（`candidate == normalized` 直接 `return null`）。也就是说它**在结构上只能改格式**，而多数输入本来就不需要改格式。它同时是跟随按键触发的额外消费。

### 1.2 目标

现场主控念完一条，字段尽快出现，一眼能确认；关键字段不依赖模型是否走运；模型调用次数有上界且可数。

## 2. 决定

| 决策 | 内容 |
| --- | --- |
| 主路径 | **多模态单跳**：音频直接交给支持音频输入的模型，一次调用同时拿到转写与字段 |
| 校对层 | **复用本地数据库**：把模型给的字段值拿去和词库/历史/会话内记录比对，命中就写库中的规范写法 |
| 救场 | 多模态失败时逐级降级到「文本 LLM」→「纯 ASR + 文本 LLM」，现有实现全部保留为救场链 |
| 上下文 | **记录级**：一条记录一个上下文，提交即销毁，记录之间不传递文本 |
| 额度 | 主路径之外的调用按**事件触发 + 硬上限**，默认 3、可调 1–5 |
| 删除 | 15 秒固定分段、累积全文、行内 LLM 建议 |

## 3. 主路径

```
录音 ──静音切分──▶ 多模态模型（一次调用）
                      │  返回 transcript + fields
                      ▼
                本地校对层（§4）
                      ▼
                 候选 → 复核面板（§7）→ 落字段
```

### 3.1 一次调用同时产出转写与字段

请求沿用已实现的 `input_audio` 通道（`lib/services/ai_recognition/http_providers.dart` 的 `_transcribeChatAudio`），但用途从「语音识别」改为「音频理解」，输出契约为：

```json
{
  "transcript": "把听到的原话转写下来",
  "fields": { "callsign": "…", "device": "…", "power": "…" },
  "uncertain": ["qth"]
}
```

- `transcript` 有两个用途：复核时给人看；救场时不必重新识别。
- `fields` 的键限定为现有集合：`callsign, device, antenna, power, qth, height, rstSent, rstRcvd, remarks`。**不返回 `time`，不返回主控呼号**（与现有一致，主控属于会话上下文）。
- `uncertain` 是可选数组，列出模型自认没把握的字段，供复核面板标黄。
- 音频格式：PCM16 WAV 已由 `lib/services/ai_audio_recorder.dart` 的 `Pcm16WavEncoder.encode` 在本地生成，直接 base64 发送；格式字段与 `audioDataEncoding` 由 provider profile 配置。

协议侧需要一个新用途：`AiProtocol.supports` 目前把 `openAiChatCompletionsAudio` 只登记给 `speechRecognition`，字段抽取只认纯文本协议。需要新增「音频 → 字段」的 kind，让同一协议既能出转写也能出字段。

### 3.2 静音切分

把固定 15 秒改为按停顿切分：在已有的 PCM16 流上计算 RMS，低于门限持续「静音时长」即切段，并设最长单段上限兜底。参数（静音门限、静音时长、最长段）可调，默认值在实施时用真实录音标定。

PCM 流不可用时（部分平台/设备）回退为**固定 4 秒窗口**，行为仍优于现状。

面板保留手动「说完这条」按钮：会场嘈杂时自动切分可能失效，人工触发是兜底。

### 3.3 记录级上下文

引入 `RecordContext`，只装本条记录的东西：已解析字段、本条记录的转写片段、本条确认与更正历史。生命周期为「开始一条 → 建立，提交或放弃 → 销毁」。

记录之间不传递任何文本或字段；跨记录唯一共享的是**词库**（持久数据，不是上下文）。这同时消除「越说越慢」和「上一条残余混入下一条」。

## 4. 本地校对层（复用数据库）

校对层是主路径的必经环节，零网络、零成本，主要工作是**检索与消歧**而不是理解句子，因此不依赖语序。

### 4.1 匹配来源

| 来源 | 用途 | 现状 |
| --- | --- | --- |
| 四类词库（呼号/设备/天线/QTH） | 主力，写回库中规范写法 | 已有，`DictionaryProvider` 已加载 |
| 近期记录 | 词库未收录但本人常填的值 | 已有 `lib/services/ai_database_context.dart` 打分 |
| 会话内已填记录 | 同一轮里前面刚念过的呼号/设备 | 数据已有，需接入校对层 |

### 4.2 匹配强度递进

1. 归一化后精确匹配（去空格、大小写、全半角、常见异体字）。
2. 音标还原：`_natoCandidates` 已能把 `Bravo Golf Five D B L` 折成 `BG5DBL`。
3. 模糊匹配：沿用 `_callsignScore` 的编辑距离容错（呼号 ≤5 位容 1、更长容 2；含数字的型号放宽到 2），以及 `_closestWindowDistance`。

### 4.3 规则

- **命中即写库中的规范写法**，而不是模型给的原文。主控把「森海克斯 GT12」念成「森海 GT 十二」，记录里落的仍是词库里那条。既提准确率，又让数据自然归一。
- **数值类不查库**：RST 用 `5[1-9][1-9]` 或中文「五九」校验；功率复用 `extractExplicitPower`；高度校验「N 楼 / N 层 / N 米」。
- **冲突消歧**：同一段证据不得被两个字段占用；多类命中时按分数与类别优先级（呼号 > QTH > 设备 > 天线）裁决，最长匹配优先。
- **匹配不上就标记为新值**，进入复核面板等待确认，不静默写入。
- **降级**：词库为空或全新用户时覆盖率自然低，主路径仍可用，只是退回「依赖模型」。

### 4.4 学习闭环

复核确认的新值，经 `rust/src/api/dictionaries.rs` 的 `apply_dictionary_ai_changes`（`BEGIN IMMEDIATE` 事务 + stateToken 乐观锁）沉淀进词库。于是**下一轮相同的念法就能本地命中**，模型调用随之减少。这是本设计的复利。

## 5. 救场链

多模态不是可选项的替代，而是主路径；但它必须有兜底，因为国产多模态模型的结构化输出支持参差（见 §10.1）。

```
多模态请求失败（网络/超时/JSON 不合法）
  → 退避重试一次
    ↓ 仍失败，且已拿到 transcript
  → 文本 LLM 抽取（现有 TextAssistantClient）
    ↓ 连转写都没有
  → 纯 ASR → 文本 LLM（即现有实现，整条保留）
```

三级降级全部沿用现有代码，不新造。触发原因写入候选的 `metadata`，便于事后统计救场率。

## 6. 成本与额度

### 6.1 成本对比

音频 token 折算（阿里官方）：**总 tokens = 音频秒数 × 12.5**，1 小时 ≈ 45,000 token。

| 路线 | 折算 1 小时音频 |
| --- | --- |
| `qwen3.8-omni-flash`（0.8 元/百万 token，全模态统一） | **≈ 0.036 元** |
| `qwen3.5-omni-plus`（音频 53 元/百万 token） | ≈ 2.39 元 |
| 豆包 Seed-ASR 2.0（纯 ASR） | 0.8 元 |
| 智谱 GLM-ASR-2512（纯 ASR） | ≈ 0.72 元 |

上表为文档原价，随地域与活动浮动，实施前需以控制台为准。

**结论：成本不再是主要约束。** 主路径的额度上限因此从「省钱」改为「避免无谓等待与幻觉叠加」。

### 6.2 额度规则

只有以下情况消耗额度：

1. 主路径首调用之后仍有未填字段，需要补救；
2. 主控又说了新的一段有效语音（补充或更正）。

**每条记录的主路径首调用不占额度**——它必须发生一次，且成本可忽略。额度覆盖的是其后的补救调用。不消耗额度的情况：主路径已填满所有字段（直接不发）；没有新语音只是同一段重试（**禁止**，这就是要砍掉的自动重试）。

- 默认上限 3，设置内可调 1–5。
- 同一段文本或音频不重复请求。
- 传输失败允许一次退避重试，不扣内容额度，但每条记录的总尝试次数封顶。
- 第二次起只发缺失字段 + 新片段，不重发整条记录。
- 复核面板显示本轮已用调用次数（`n / 上限`），成本可见。

因此每条记录的调用次数上界是「1（主路径）+ 上限」，一轮 59 人点名最坏 59 × 4 = 236 次，实际远低于此。这个上界是可算的，不像现状随时长线性膨胀。

## 7. 确认与更正交互

在现有 `_AiRecognitionReviewPanel` 上改，不新造面板。

1. **字段带来源标记**，按**产出该字段的那次调用**划分：`本地命中`＝校对层在库中匹配到；`推断`＝主路径给出但库中无对应；`模型补充`＝救场链产出。一眼看出哪些需要人看。
2. **一键采纳只采纳高置信**：`全部采纳` 只吃 `本地命中` 项；`推断` 与 `模型补充` 必须单独确认或编辑。常见的「念完就确认」是一次点击。
3. **更正呈现为「旧值 → 新值」**，不是新增。一个字段只有一个值，更正进撤销栈。
4. **保留「再听一句」**：手动发起一次识别，占一次额度，用于主控让对方重念之后。
5. **不弹模态**：解析与救场在后台跑，字段逐项出现，等待期间可继续操作。

同一条记录内再次说话且某字段已有值时，判为更正（走现有 `AiCandidateGuard` 的 `replaceWithConfirmation`），不会出现两个呼号。记录提交后再改属于普通记录编辑，不唤醒 AI 上下文。

## 8. 配置与迁移

| 设置项 | 变化 |
| --- | --- |
| 语音识别（ASR profile） | 保留，成为救场链末端 |
| 文字助手 | 保留，从必需降为救场链中段 |
| 多模态（音频理解）profile | **新增**，主路径。复用 `AiProviderProfile` 结构，新增 kind |
| 慢路径上限 | **新增**，默认 3，范围 1–5 |
| 静音切分参数 | **新增**，门限/静音时长/最长段 |

迁移：现有 ASR 与文字助手配置原样保留，升级后立即可用作救场；用户在设置里补一条多模态 profile 即启用主路径。凭据仍走 `AiCredentialStore` + 平台安全存储，不落 `shared_preferences`。

**删除**：`TextAssistantTasks.suggestInline` 及其调用链（`lib/widgets/log_form.dart` 的 `_requestInlineAiSuggestion` / `_adoptInlineAiSuggestion`）。已有的字典即时补全是确定性、零成本的，行内建议想做的事它本来就在做。

## 9. 顺带修掉的既有缺陷

这三处是探查中发现的客观缺陷，且救场链会提高相关代码的使用频率，因此纳入本次范围：

1. **文字助手不禁用重定向**：`lib/services/text_assistant.dart` 的 `_postJson` 用 `package:http` 默认跟随重定向，`Authorization` / `x-api-key` 可能被转发到其他 origin。ASR 的 `http_transport.dart` 已明确 `followRedirects = false` 并禁止隐式重定向转发凭据，两者应对齐。
2. **文字助手无响应体上限**：ASR 有 2MB 上限（`maxResponseBytes`），文字助手没有。
3. **Excel 导入泄漏 HTTP 客户端**：`lib/widgets/export_panel.dart` 的 `_importExcel` 创建 `createTextAssistantClient(...)` 后全程无 `client.close()`，每次导入泄漏一个客户端；字典与行内建议两条路径都有 `finally { client.close(); }`。

另外把 `languageHint` 接到转写调用上：`AiRecognitionRuntime.transcribe` 目前未传该参数，而 model/provider 与文档都声明支持「存在语言提示时发送」。

## 10. 前置实验与验收指标

### 10.1 前置实验（必须先做，结论决定主模型）

`qwen3.8-omni-flash` 的结构化输出支持情况未能从文档确认，而 `qwen3.5-omni-flash` 明确**不支持**。这直接决定 JSON 合法率与救场链触发频率。

做法：取真实点名录音（至少 20 条，覆盖呼号字母混读、中文 QTH、设备型号混读），对三个候选模型跑同一份 prompt：`qwen3.8-omni-flash`（首选）、`qwen3.5-omni-plus`（支持 JSON Object 的保底），以及硅基流动上的一个开源音频模型作对照。比较：

| 指标 | 说明 |
| --- | --- |
| JSON 合法率 | 一次解析成功、无需重试的比例 |
| 呼号准确率 | 逐字符正确率，以及**经本地词库校正后**的最终正确率 |
| 端到端耗时 | P50 / P95 |
| 字段召回 | 各字段被正确填出的比例 |
| 单条成本 | 实测 token 用量折算 |

若 `qwen3.8-omni-flash` 的 JSON 不稳，主模型换 `qwen3.5-omni-plus`（支持 JSON Object，约 2.4 元/小时，仍远低于预算敏感线）。

### 10.2 验收指标

- **本地校对覆盖率**：不依赖模型补充、仅靠库匹配即填对的字段比例。
- **端到端延迟**：从切段到候选出现，P50 / P95。
- **每条记录平均模型调用次数**（含救场）。
- **救场链触发率**与**降级层级分布**。
- 回归方式：表驱动语料（转写 + 期望字段），纳入现有 `flutter test`。

## 11. 非目标

- 不做本地（端侧）语音识别。若将来要离线可用，那是另一个设计。
- 不做流式增量转写（WebSocket 逐字出）。本设计接受「一句话一次」的交互，不追求亚秒级。
- 不改动协作、同步、导出等与 AI 无关的部分。
- 不引入对话历史。每次请求都是无状态单轮。

## 12. 风险

| 风险 | 应对 |
| --- | --- |
| 多模态模型 JSON 不稳定 | 救场链是强制项；§10.1 先实测再定模型 |
| 模型幻觉呼号 | 本地词库模糊校正 + `AiCandidateGuard` 强制人工确认，不静默写入 |
| 会场嘈杂导致静音切分失效 | 保留手动「说完这条」按钮；回退固定窗口 |
| 音频后端的字段名/采样率各家不同 | 沿用 profile 里已有的 `audioFormat` / `audioDataEncoding` / `requestTemplate` 开关，不按模型名猜 |
| 单价随活动变化 | 复核面板显示调用次数；成本按实测折算而非按标价承诺 |
| 记录级上下文被误用（跨记录复用） | `RecordContext` 只在开始记录时创建，提交即销毁，并在测试中断言不跨记录 |
